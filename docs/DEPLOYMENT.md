# Развёртывание и обновление

Инструкции относятся к версии после модернизации по аудиту от 12 ноября 2026 года. Реальную доступность внешней PostgreSQL, работу proxy и телефона необходимо проверять в конкретной установке.

## Модель размещения

Поддерживайте один основной deployment path и постоянные данные отдельно от образа приложения. Веб-процесс запускает Gunicorn; миграции выполняются отдельным release-шагом. `collectstatic` собирает публичные файлы интерфейса. Фотографии пользователей хранятся отдельно и выдаются только после проверки доступа.

Для личного размещения допустим SQLite на постоянном диске при подходящей нагрузке. Для нескольких процессов и командного использования предпочтительна PostgreSQL с проверенными миграциями, соединениями и резервированием. Переход на PostgreSQL не делает автоматически правильными права доступа или резервные копии.

## Обязательная production-конфигурация

Начните с `.env.example`. Не коммитьте заполненный файл.

| Переменная | Назначение |
|---|---|
| `DEBUG` | `False` в production; `True` только в локальной разработке |
| `SECRET_KEY` | Длинный случайный секрет из защищённых настроек среды |
| `PUBLIC_BASE_URL` | Канонический HTTPS origin, который будет напечатан в QR |
| `ALLOWED_HOSTS` | Точные имена хостов этой установки; без схемы и общих платформенных wildcard |
| `CSRF_TRUSTED_ORIGINS` | Собственные доверенные origins с HTTPS-схемой |
| `MEDIA_ROOT` | Постоянный приватный каталог фотографий/файлов |
| `SQLITE_PATH` | Путь к постоянному SQLite-файлу, если не используется `DATABASE_URL` |
| `DATABASE_URL` | Соединение PostgreSQL, если она используется; храните как секрет |
| `DB_SSLMODE` | Проверка TLS PostgreSQL: production по умолчанию `verify-full`; настройка `disable` допустима только по осознанному решению в защищённой сети |
| `TRUST_PROXY_HTTPS` | Включать только за единственным доверенным TLS proxy |

Вход ограничивается счётчиком неудачных попыток django-axes в БД. В текущей политике учитываются имя пользователя и IP socket peer; forwarded IP-заголовкам приложение по умолчанию не доверяет. За общим proxy нужен дополнительный корректно настроенный edge limiter: общий адрес proxy не равен адресам отдельных клиентов. Для разблокировки доверенный оператор может использовать `python manage.py axes_reset`.

Проверяйте дополнительные параметры в текущем `.env.example` и `config/settings.py`: они определяют поддерживаемый синтаксис значений. Не копируйте настройки старой версии с `*.railway.app`, публичным fallback SECRET_KEY и подавленными security checks.

Настройки требуют безопасных значений для production и должны отказывать при их отсутствии. Не включайте `DEBUG`, чтобы обойти ошибку конфигурации на публичном сервере.

## HTTPS и reverse proxy

Terminate TLS на доверенном proxy или платформе. При передаче forwarded headers убедитесь, что внешний клиент не может подделать их и обойти proxy. Не включайте доверие к произвольному `X-Forwarded-Proto` или `X-Forwarded-For` без соответствующей настройки границы доверия.

Проверьте переход HTTP → HTTPS, secure cookies, CSRF при входе, допустимые hosts и работоспособность формы после входа. `SECURE_HSTS_*` имеет смысл только после проверки HTTPS. Для внутренней health/readiness-проверки используйте соответствующий маршрут приложения и конфигурацию платформы.

Не добавляйте публичный `location /media/ { alias ...; }` к Nginx. Он обходит принадлежность файла пространству. WhiteNoise предназначен для static-файлов, а не для приватного пользовательского media.

## Docker Compose для локальной проверки

`compose.yaml` использует SQLite и постоянный volume `/data`; это локальная конфигурация, не готовое публичное HTTPS-размещение. Сначала подготовьте `.env`, затем:

```bash
docker compose build
docker compose run --rm web python manage.py migrate --noinput
docker compose run --rm web python manage.py createsuperuser
docker compose up -d
```

Не удаляйте volume при обычном обновлении. Приложение запускается непривилегированным пользователем; проверьте права на подключённом каталоге. Для Railway используется Dockerfile с отдельной release-миграцией. SQLite и media требуют постоянного volume; внешний PostgreSQL не заменяет постоянное хранение фотографий.

## Первое размещение

1. Настройте постоянный диск/volume для БД и `MEDIA_ROOT`, HTTPS и секреты.
2. Установите закреплённые зависимости под Python 3.14 с проверкой хэшей.
3. Выполните release-команды в каталоге приложения:

```bash
python manage.py check --deploy
python manage.py migrate --noinput
python manage.py collectstatic --noinput
```

4. Создайте администратора через `python manage.py createsuperuser`.
5. Запустите штатную команду Gunicorn из deployment-конфигурации.
6. Создайте отдельные обычные учётные записи для участников. Staff и superuser не являются повседневными семейными ролями.
7. Проверьте вход, создание пространства, фотографию с `DEBUG=False`, переход по этикетке с другого устройства, изоляцию второго пространства и резервную копию.

Не устанавливайте предсказуемый пароль или общий аккаунт для пользователей. Открытой самостоятельной регистрации в текущем сценарии нет.

## Безопасное обновление старой установки

До первого `migrate` новой версии:

1. Зафиксируйте текущую версию приложения, Python, конфигурацию и зависимости.
2. Запланируйте окно обновления и остановите записи. Сохраните согласованную копию SQLite или PostgreSQL и файлов media. Скопируйте конфигурацию в защищённое место, отдельно от публичного репозитория.
3. Восстановите копию в отдельный каталог/тестовую среду. Выполните миграции и проверки там.
4. Убедитесь, что старые вещи, связи и файлы сохранились, а данные не стали доступны посторонним.
5. Только после этого обновляйте рабочую установку. Выполните release-миграции, соберите static и перезапустите веб-процессы.
6. Проверьте ключевой путь с обычным пользователем и с пользователем другого пространства. Сохраните проверенную копию до окончания периода наблюдения.

Миграция переносит старые вещи, категории и места в закрытое пространство «Импортированные данные». Автоматического владельца по первому найденному пользователю нет. Суперпользователь сначала проверяет содержимое и явно назначает существующего пользователя:

```bash
python manage.py assign_workspace_owner WORKSPACE_ID USERNAME
```

Запускайте management-команды только доверенным оператором с доступом к окружению приложения. Доступ к командной строке и базе уже является административной привилегией.

Rollback к старому коду после миграции схемы может быть небезопасен. Рабочий вариант восстановления — согласованная пара предыдущего кода/конфигурации и проверенной резервной копии; не сбрасывайте рабочую БД командами Git.

## Резервная копия SQLite и media

Команда создаёт новую резервную копию и не должна перезаписывать существующий файл:

```bash
python manage.py backup_inventory --output /secure/backups/homeinventory-2026-11-12.zip
```

Архив содержит конфиденциальные данные. Храните его вне checkout и публичных каталогов, ограничивайте доступ и передавайте по защищённому каналу. Шифрование диска/внешнего backup storage и политика retention относятся к эксплуатации; сам ZIP не следует считать зашифрованным.

Согласованный снимок SQLite не делает одновременные изменения media атомарными с БД. На время полного backup остановите записи/веб-процессы или используйте согласованный snapshot подходящего хранилища. Копия, которую не восстанавливали, не подтверждает восстановимость.

Для PostgreSQL используйте поддерживаемый `pg_dump`/managed backup, согласованный с media. Не считайте SQLite-команду заменой резервированию внешней PostgreSQL. Проверяйте совместимость версии `pg_dump`, шифрование и доступность внешнего backup storage.

## Проверка восстановления

Остановите приложение и восстановите архив в **новый**, несуществующий путь БД и новый, ещё не существующий путь каталога media:

```bash
python manage.py restore_inventory \
  --archive /secure/backups/homeinventory-2026-11-12.zip \
  --database /srv/restore-check/db.sqlite3 \
  --media-root /srv/restore-check/media
```

Команда предназначена для offline-восстановления и проверки контрольных сумм/путей. Она не должна перезаписывать существующую базу и пользовательские файлы. После восстановления запустите отдельную среду с восстановленными путями, проверьте количество объектов, связи, фотографии и доступ пользователей. Только после проверки меняйте рабочие пути.

Архивная копия установки и пользовательский переносимый архив пространства решают разные задачи: полная копия предназначена оператору; перенос пространства не должен выдавать пользователю чужие данные и права.

## Перенос пространства через интерфейс

Переносимый ZIP сохраняет каталог: категории, места, контейнеры, вещи, цены, даты, описания и фотографии. Это **не полная операционная резервная копия**: пользователи, роли, текущие выдачи и журнал операций не восстанавливаются в независимую копию. Для точного восстановления установки используйте полный backup БД и media.

Импорт проходит предпросмотр и подтверждение и создаёт новое приватное пространство, принадлежащее импортирующему пользователю. Учётные записи и memberships не восстанавливаются из недоверенного архива; участники назначаются заново явно.

Не открывайте импорт в существующее пространство как способ объединения данных без отдельного правила конфликтов. Проверяйте лимиты, корректность файлов и повторный импорт. Публичная публикация импортированного имущества требует нового явного решения владельца. При копировании пространства идентификаторы этикеток создаются заново: для новой копии нужно перепечатать этикетки. В полном операционном восстановлении исходные идентификаторы сохраняются.

## Что проверить после каждого релиза

- Анонимный запрос не получает частные данные, CSV или media.
- Наблюдатель не изменяет и не удаляет записи; внешний workspace недоступен по прямому URL и подставленным ID.
- Фото и QR работают с `DEBUG=False`, после restart и после нового deployment.
- QR содержит правильный HTTPS origin; существующая физическая этикетка остаётся пригодной.
- Кириллический поиск, фильтры и пагинация работают на выбранной СУБД.
- Выдача одного предмета не допускает две активные записи; возврат повторяется безопасно.
- Отзыв публикации закрывает публичную карточку и не раскрывает личные поля.
- Получен и восстановлен свежий backup; срок хранения и доступ к нему соответствуют ожиданиям владельца.

Проверка в локальной среде не подтверждает работу телефона, внешней базы, оборудования печати или конкретного облачного deployment. Эти результаты фиксируйте отдельно.
